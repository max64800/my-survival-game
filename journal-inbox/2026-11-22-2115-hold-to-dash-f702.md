## F702: hold-to-dash (tap = short dash, hold = longer dash)

**What we did:** We already had a dodge-roll (Ctrl): a quick roll that always lasts the same short time. The
owner wanted it to work like a real dash — a quick tap still gives the short roll, but holding Ctrl down keeps
the dwarf going for longer, up to a cap.

How it works, simply: the roll already moves at one steady speed for a fixed time (like a sprinter running a
fixed number of steps). Instead of always stopping at that fixed time, we now check "is the button still held,
and have we not gone past the cap yet?" If yes, it just keeps counting instead of stopping. The cap is set to
match how long the ROLL ANIMATION plays (0.75 seconds) — the drawing of the dwarf tumbling — so his body never
slides past what the animation shows him doing (the project calls this "feet skating," a thing we specifically
avoid).

**Hurdles and how we fixed them:**
1. The new test for this (a robot that taps Ctrl, then holds Ctrl, and checks the hold goes farther) kept
   failing — the dodge never started at all, even for a plain tap, even though every other check (stamina,
   being "in game," etc.) looked fine. After several rounds of debug printing, the real cause was a timing
   quirk: in the test, pressing a key by script and immediately checking "was it just pressed?" doesn't always
   line up with the one exact game-tick the code is watching for, because the test fast-forwards one tick at a
   time instead of running in real time. The project already had a fix for this exact problem for the Jump key
   (a hidden "pretend-pressed" switch just for tests/robots) — we added the same kind of switch for Dodge
   (`bot_dodge` on the dwarf) so the test can trigger a dodge reliably without fighting the clock.
2. Before trusting the test, we deliberately broke the real fix on purpose (made "holding it" count for
   nothing) and reran the test — it correctly failed, proving the test actually catches the bug and isn't just
   passing by luck. Then we put the real fix back and it passed again.
3. We tried to boot a real test game to watch the dash with our own eyes, but another Claude session working
   on this same project right now has an unfinished file (`src/ui/hitbox_debug.gd`, likely their work on the
   hitbox-viewer item) that currently stops the whole game from starting at all (a script error). That's their
   work-in-progress, not ours, so we left it alone and didn't boot a live game this time — the automated test
   (plus the deliberate "break it, check it fails, fix it, check it passes" check above) stands in for that.
4. Also found while running the full test list earlier (for F701): the game can actually crash (not just fail
   a check) during one dungeon-fight test, inside code we didn't touch. Added it to FEEDBACK.md's "Claude
   noticed, waiting for your OK" list rather than fixing it ourselves, since the owner didn't ask for it and our
   rule is to check before touching things we just happened to notice.
